# NetOps 平台数据库设计规范

> 来源：design-db（@user_a4c2f3d2，v1.0.2）数据库设计规范，2026-10-24 按平台实际落库评审后固化。
> 适用范围：本平台全部存储库（MySQL/OceanBase/Oracle/达梦/Kingbase/PG/SQLite）与时序库（TDengine/InfluxDB/builtin）。
> 模型定义：`backend/internal/model/model.go`；全量建表入口：`backend/internal/appinit/appinit.go` `AllModels()`；迁移方式：GORM AutoMigrate（DDL 随代码进版本控制）。

## 1. 命名约定

| 对象 | 规则 | 平台现状 |
|---|---|---|
| 表名 | 小写 + 下划线复数，如 `users`、`alert_events` | ✅ 全部合规（GORM 复数表名） |
| 关联表 | `{表A}_{表B}` 字母序 | ✅ 关联表独立 id 主键 + 双 FK 索引 |
| 列名 | 小写 + 下划线，如 `node_uuid` | ✅ 全部合规 |
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT`（GORM uint） | ✅ 每表必备，无缺失 |
| 外键列 | `{表名单数}_id`，如 `group_id`、`device_id` | ✅ 全部符合 |
| 布尔 | `is_xxx` / `enabled` / `enable`（TINYINT(1)） | ✅ 无 ENUM，全部布尔 |
| 时间 | `xxx_at`（DATETIME(3)） | ✅ 无 TIMESTAMP（无 2038 隐患） |
| 索引 | 普通 `idx_{表}_{列}`，组合 `idx_{表}_{列1}_{列2}`，唯一 `uk_{表}_{列}` | ⚠️ GORM 唯一索引自动命名 `idx_`，`uk_` 前缀为演进项（改前缀需重建索引） |

## 2. 必备字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | 全部表具备 |
| `created_at` / `updated_at` | DATETIME(3) | 主要业务表已含；`docker_hosts`/`k8s_clusters`/`notify_configs`/`alert_rules`/`config_backup_devices` 等配置类小表未含——可接受（配置表量小，无审计诉求），新表一律补齐 |
| `created_by` / `updated_by` | — | 平台采用独立 `audit_logs` 审计表方案，业务表不冗余审计字段 ✅ |

## 3. 数据类型

| 场景 | 平台做法 | 结论 |
|---|---|---|
| 主键/数量 | `uint` → BIGINT UNSIGNED | ✅ |
| 短文本 | `VARCHAR(n)` 全部给长度（8~512） | ✅ 无裸 VARCHAR |
| 长文本 | `TEXT`/`MEDIUMTEXT`/`LONGTEXT`（证书/脚本/正文/日志） | ✅ |
| 布尔 | `bool` → TINYINT(1) | ✅ 无 ENUM |
| JSON | 存 TEXT 列（ParamsJSON/SchemaJSON/Config/Tags 等） | ⚠️ MySQL 5.7+/8.0 可用原生 JSON，迁移成本高，标注演进项 |
| 金额/阈值 | `DECIMAL(10,2)`（AlertRule.Threshold/AlertEvent.Value） | ✅ |
| 监控指标 | `FLOAT`/`DOUBLE`（CPU/内存/带宽/速率） | ✅ 瞬时采样值不涉累计精度 |
| 百分比 | `float64` | ⚠️ 规范建议 DECIMAL(5,2)，监控采样场景 FLOAT 精度足够，标注演进项 |

## 4. 索引设计（本规范核心落地项）

**原则**：WHERE/JOIN/ORDER/GROUP 列建索引；组合索引等值在前、范围在后、最左前缀；低基数列不建单列索引；组合索引 ≤5 列。

### 4.1 已落地索引矩阵（2026-10-24 两轮补齐，全部实测落库）

| 表 | 索引（原有） | 本次新增 | 服务的查询路径 |
|---|---|---|---|
| users | uk username；idx email/employee_no/api_token | — | 登录、工号/邮箱检索 |
| audit_logs | idx user_id/created_at | **username**、**(user_id,created_at)** | 审计按用户/时间线查询 |
| alert_events | idx rule_id/target/group_key | **created_at**、**metric**、**(group_key,acked)**、**(target,acked)** | 告警列表排序、按指标筛选、收敛去重、拓扑页未确认告警 |
| device_logs | idx source/device_name/level/created_at | **ip**、**(device_name,created_at)**、**(level,created_at)** | 设备日志时间线、24h 错误统计、按 IP 检索 |
| task_logs | idx device_id/created_at | **(device_id,created_at)** | 采集历史时间线 |
| bind_devices | （仅主键） | **ip** | IPAM 绑定设备查询 |
| config_backup_devices | idx node_id | **ip** | 备份设备按 IP 查询 |
| script_templates | idx code/vendor/device_type/category | **(vendor,device_type)** | 模板列表筛选 |
| ip_records | idx subnet_id/ip/bind_device_id | **(subnet_id,ip)** | IP 占用唯一性检查 |
| ts_archives | uk (metric,field,tags_key,day) | — | 每日归档 upsert（天然组合唯一） |
| ts_archive_retries | uk (metric,day) | — | 补传重试 |
| certificates | idx node_uuid/fingerprint | — | 证书检索/指纹特征标签 |
| monitor_devices | idx group_id/ip/node_uuid | — | 组/节点/设备查询 |
| 其余表 | 主键 + 按需单列 | — | 配置类小表不建冗余索引 |

### 4.2 未加索引的查询路径（接受全表扫描，标注原因）

- `LIKE '%x%'` 模糊检索（user/device_log/ipam）——`%` 前缀通配无法走 B-Tree，数据量达到万级再评估全文索引
- 低基数列等值过滤（`enabled=true`、`type`、`status`、`level` 单查）——选择性低，索引收益为负
- `DATE(created_at)=?` 函数包裹——无法索引，AI 巡检日统计量小可接受

## 5. 约束

| 约束 | 平台现状 |
|---|---|
| NOT NULL | 关键业务列已声明；可选列允许 NULL（正确语义） |
| DEFAULT | 状态/开关/阈值列均有默认值 ✅ |
| UNIQUE | 业务唯一键：username、email 未强制（允许空）、cidr、code、key、node_uuid、TopoPos.node_id、TsArchive 组合 ✅ |
| PRIMARY KEY | 每表必备 ✅ |
| 外键 | 全部逻辑外键（代码层保证），FK 列均有索引 ✅ |
| CHECK | 未使用（代码层校验）——演进项 |

## 6. 软删除

平台业务表无物理删除需求场景使用；删除策略：
- 审计/日志/告警采用**保留窗口 + 定时清理**（`main.go`/`devicelog.go` 按 created_at 窗口 Delete）
- 证书/节点等主数据按业务状态字段（valid/expired/offline）标记，不软删
- `ip_records` 使用 `Unscoped()` 真删（IP 释放语义正确）
- **演进项**：如未来需要"可恢复删除"（如节点/设备），用 `gorm.DeletedAt` 软删

## 7. 迁移管理

- 全部 DDL 由 GORM AutoMigrate 随代码版本控制 ✅（改模型 → 重新部署 → 自动迁移）
- 新加字段给 DEFAULT、不删旧字段（向兼容）
- 破坏性变更分步：add column → 代码适配 → drop column（分版本）
- **铁律**：生产禁删表、删列、改名；手工 DDL（本次索引补齐）已同步回 model.go，保证新环境一致性

## 8. 时序库（TDengine / InfluxDB）模型规范

- TDengine 表模型：`t_<metric>_<taghash>`，列 `(ts TIMESTAMP, fname VARCHAR(64), val DOUBLE)`，主键 `ts` ✅
  - 度量+字段+标签哈希拆表，避免单表膨胀；`t_` 前缀 + 小写下划线 ✅
  - 无冗余二级索引（TDengine 按主键时序天然索引）✅
  - 建库 `KEEP 30 DURATION 1`，原始数据保留 30 天，由 `ts_archives` 每日归档进存储库长期保存 ✅
- InfluxDB：`<metric>_<field>` 度量命名 + tag 排序写入，InfluxQL 服务端 `GROUP BY time()` 聚合 ✅
- 查询聚合：TDengine 服务端 `PARTITION BY fname INTERVAL(ms)` 下推，传输量降 10 倍 ✅

## 10. 演进项（评审标注，未实施）

| 项 | 价值 | 成本/风险 |
|---|---|---|
| 唯一索引前缀统一 `uk_` | 命名规范一致 | 需 DROP+ADD 重建生产索引，收益低 |
| JSON 列升级原生 JSON 类型 | 校验/查询能力 | 迁移大表风险，当前 TEXT 足够 |
| 日志大表（audit/device/task_logs）按时间分区 | 清理效率、索引瘦身 | 需迁移历史数据 |
| 布尔列 COMMENT 注释 | 可维护性 | 全量 MODIFY COLUMN DDL |
| 带宽/百分比列改 DECIMAL | 规范严格度 | 破坏现有数据/前端展示 |
| CHECK 约束 | 数据完整性 | 代码层已校验 |
